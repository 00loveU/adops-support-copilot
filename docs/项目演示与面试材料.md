# AdOps Support Copilot 项目演示与面试材料

> 使用原则：只讲自己能够解释和现场演示的内容。项目使用模拟广告数据，是个人 AI 应用项目，不包装成真实生产系统。

## 一、3 分钟项目演示流程

### 演示前准备

```powershell
docker compose up -d
docker compose ps
```

打开 `http://127.0.0.1:8080`，准备两个账号：

- 运营账号：`operator1` / `Operator123!`
- 管理员账号：`admin1` / `Admin123!`

### 0:00—0:25：介绍问题与方案

讲解词：

> 这是一个面向内部广告运营人员的投放诊断助手。运营过去需要分别查指标、对照规则并整理排查建议，这个项目把流程整合成自然语言入口。系统使用 ReAct Agent 按需调用指标、诊断和知识检索工具，但数值计算和异常判断仍由确定性代码完成，避免模型编造业务数据。

### 0:25—1:25：完成一次异常诊断

1. 使用运营账号进入“广告诊断工作台”。
2. 选择计划 `CMP004`，日期选择 `2026-09-08`。
3. 输入“分析异常原因”并提交。
4. 展示回答中的确认事实、核心指标、命中规则、可能原因和建议。
5. 向下展示知识来源、Agent 执行过程和 Trace ID。

讲解词：

> Agent 先调用异常诊断工具，工具从 SQLite 读取模拟投放数据，计算 CTR、CVR、CPA 和 ROAS，再使用已确认的规则判断异常。本次命中低转化率规则。LLM 只负责把结构化证据组织成易读回答。页面还展示真实知识来源和安全的工具执行摘要，不暴露模型隐藏思维链。

### 1:25—2:05：展示 Trace 可观测性

1. 切换管理员账号。
2. 打开“Trace 排障”。
3. 找到刚才请求，展示 `request_received`、`slot_validation`、`metric_query`、`anomaly_diagnosis`、`agent_orchestration` 和 `record_saved` 时间线。

讲解词：

> 每次请求都有唯一 Trace ID。系统记录的是输入参数、工具摘要、状态和耗时等可观察事实，而不是隐藏推理。管理员可以按正常、降级和失败筛选，因此模型或工具出现问题时，可以定位失败阶段。

### 2:05—2:45：展示评估闭环

1. 从失败、降级或“没帮助”的 Trace 创建评估候选。
2. 打开“评估候选”，说明管理员需要填写预期意图、预期工具或关键结果，并人工确认后才能加入评估集。
3. 打开“离线评估”，展示 15 条固定用例、能力通过率、版本快照和历史批次。

讲解词：

> 我没有让线上失败样本自动成为标准答案，而是增加了人工复核门禁。确认后的样本进入固定评估集，后续修改提示词、规则或代码时重新运行。每个批次保存模型、提示词、代码、知识和评估集版本，避免只看到分数变化却不知道运行条件。

### 2:45—3:00：总结边界

讲解词：

> 项目通过 Docker Compose 一键启动，Nginx 托管 React 并反向代理 FastAPI。当前只使用模拟数据、提供只读建议，不连接真实广告平台。它重点验证的是 Agent 工具编排、结果可追溯和从线上反馈到离线回归的工程闭环。

## 二、面试讲解稿

### 1. 一分钟项目介绍

> AdOps Support Copilot 是我针对广告运营场景设计的个人 AI 应用项目。它解决的是运营人员查询指标、判断异常和查找规则需要在多个系统之间切换的问题。前端使用 React，Nginx 提供静态页面和 API 反向代理；后端使用 FastAPI，ReAct Agent 根据问题选择指标查询、异常诊断或知识检索工具；数据和小规模知识库使用 SQLite 与 FTS5。为了让结果可信，我没有让大模型直接计算指标或决定异常，而是用 Python 确定性计算和规则判断，LLM 只做意图理解、工具选择和回答组织。同时系统记录结构化 Trace，并把失败、降级和负反馈样本经过人工复核加入离线评估集，形成可回归的质量闭环。

### 2. 为什么使用 Agent，而不是普通聊天机器人？

普通聊天机器人主要依靠模型已有知识回答，无法保证拿到当前广告计划的数据。这个场景需要根据问题动态决定下一步：参数不完整时先澄清，查询指标时读取数据库，诊断时执行规则，规则问答时检索知识。因此使用 ReAct Agent 作为编排层，但只开放三个只读工具，并设置最多 5 步，限制成本和失控风险。

### 3. 一次请求怎样执行？

```text
浏览器 → Nginx → FastAPI → 参数检查
       → ReAct Agent 选择工具 → Python 工具查询/计算/检索
       → LLM 基于工具证据组织回答
       → 保存会话、处理记录和 Trace → 返回前端
```

如果缺少计划或日期，系统保存短期澄清状态，用户补充后继续原任务。会话和消息持久化到 SQLite，所以刷新或切换页面后仍能恢复。

### 4. 怎样控制大模型幻觉？

- CTR、CVR、CPC、CPA、ROAS 由 Python 根据原始字段计算。
- 异常结论只能来自已确认的模拟规则。
- 规则问答只引用 FTS5 实际检索到的来源。
- LLM 输入中提供结构化事实，并约束其区分“确认事实、可能原因、建议”。
- 模型失败时使用确定性结果生成降级回答，不伪造成功。

### 5. 为什么用 SQLite FTS5，而不是向量数据库？

第一版知识量小，规则编号、指标名称和异常类型等关键词明确，FTS5 已能完成检索，而且不需要额外部署 Embedding 服务和向量数据库。它降低了两天原型的部署与调试成本。只有当知识规模扩大、用户表达与文档关键词差异明显，并且离线评估证明召回率不足时，才需要升级为混合检索或向量检索。

### 6. Trace 记录什么？为什么不展示 Thought？

Trace 记录请求、参数校验、工具调用、输入输出摘要、来源、状态、耗时、错误和降级信息。这些事实足够用于排障和评估。模型隐藏 Thought 不稳定，可能包含敏感信息，也不是验证业务正确性的可靠证据，因此运营端只展示安全的工具执行过程。

### 7. 离线评估怎样形成闭环？

```text
线上 Trace / 用户反馈
  → 创建候选样本
  → 管理员补充预期并人工确认
  → 加入固定评估集
  → 修改后运行离线评估
  → 对比批次与失败项
  → 继续改进
```

评估优先使用确定性规则，检查意图、参数、工具、指标、异常规则、来源和澄清行为。批次同时保存模型、提示词、代码、知识库和评估集版本，使结果可复现、可比较。

### 8. Docker 和 Nginx 分别做什么？

Docker Compose 负责统一启动前端、后端并挂载持久化数据卷。前端镜像先用 Node.js 构建 React，再由 Nginx 提供静态文件。Nginx 把浏览器的 `/api` 请求转发到 Docker 网络中的 FastAPI 后端，从浏览器视角只有一个应用入口，也避免把后端地址写死在前端。

### 9. 项目中最值得讲的取舍

- 使用模块化单体，而不是微服务：当前用户量和开发周期不需要分布式复杂度。
- 使用单 Agent 加确定性工具，而不是多 Agent：减少模型调用、状态同步和调试成本。
- 使用 FTS5，而不是直接上向量数据库：先用最简单方案满足小规模规则检索。
- 使用进程内离线评估，而不是消息队列：管理员手动运行的小数据集不需要分布式任务系统。
- 只提供建议，不执行投放修改：把有风险的写操作排除在第一版范围外。

### 10. 项目局限和后续方向

当前项目使用模拟数据，SQLite 适合单机演示，不代表已验证真实流量下的并发与稳定性；离线评估集目前规模较小，也可能存在对固定规则的偏向。下一步只有在接入真实脱敏数据后，才考虑扩充时间序列诊断、增加检索召回评估，并根据压测结果决定是否迁移 PostgreSQL 或引入异步任务队列。

### 11. 常见追问的简短回答

**问：15/15 是否证明系统已经很好？** 不能。它只说明当前版本通过了这 15 条固定用例，需要继续加入真实失败样本、边界样本和对抗样本。

**问：Agent 选错工具怎么办？** Trace 会记录实际工具；离线评估检查预期工具，失败样本经人工复核后加入回归集。

**问：为什么不让 LLM Judge 评分所有内容？** 确定性问题用规则评分更稳定、更便宜。LLM Judge 只适合规则难覆盖的表达质量，并且不能替代人工复核。

**问：这是 RAG 吗？** 规则问答部分属于轻量检索增强：先用 FTS5 找到知识片段，再把片段交给 LLM 组织回答。它没有使用 Embedding 和向量数据库。

## 三、简历项目经验

### 推荐版本

**AdOps Support Copilot｜广告投放智能诊断助手（个人项目）**

`React` `FastAPI` `ReAct Agent` `Function Calling` `SQLite FTS5` `Docker Compose` `Nginx`

- 面向内部广告运营场景，设计并实现集指标查询、异常诊断、规则问答和参数澄清于一体的 Agent 应用；ReAct Agent 在最多 5 步内按需调用三个只读业务工具，并持久化短期多轮会话。
- 将 LLM 与业务计算解耦：使用 Python 确定性计算 CTR、CVR、CPC、CPA、ROAS，并按已确认规则判断异常；基于 SQLite FTS5 返回真实知识来源，输出“事实—可能原因—建议—来源”的可追溯结果。
- 建设结构化 Trace 与安全降级能力，记录参数校验、工具输入输出摘要、耗时和状态；模型不可用时保留确定性诊断结果，前端展示工具执行过程但不暴露隐藏思维链。
- 打通“Trace/负反馈—候选样本—人工复核—固定评估集—批次对比”评估闭环；内置 15 条用例并保存模型、提示词、代码、知识库和评估集版本快照，当前演示批次通过 15/15。
- 使用 Docker Compose 编排前后端，采用 Nginx 托管 React 静态资源并反向代理 FastAPI，SQLite 数据通过命名卷持久化，实现本地一键启动。

### 一行精简版

设计并实现广告投放智能诊断 Agent，以确定性指标/规则工具约束 LLM 幻觉，并通过结构化 Trace、人工复核和版本化离线评估形成质量闭环，使用 Docker Compose + Nginx 完成前后端部署。
